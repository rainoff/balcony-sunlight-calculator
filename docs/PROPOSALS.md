# 發展提案

這份文件接在 2026-09 的活動投稿之後。作品已經能展示，接下來想讓它真的派上用場。
下面是候選方向，**不是定案**。歡迎開 issue 或 PR 討論、認領。

## 現況（2026-09-25 讀程式碼盤點）

- 全部功能在 `index.html` 一個檔案，約 1600 行。沒有 build、沒有套件依賴、沒有測試檔。
- 太陽位置用 NOAA 公式在瀏覽器即時算，不打外部 API。唯一外部連線是 Wikimedia Commons 的植物照片。
- 使用者已經可以調：陽台朝向、寬、深、雨遮高、女兒牆高、對面建築距離與樓層，以及三種遮蔽物的開關。
- 寫死的東西：
  - 地點固定台北（`index.html:504`，LAT/LON 常數）。
  - 網址只記選了哪種植物（`index.html:1403`）。陽台設定不進網址、不存瀏覽器，換一台手機要重填。
  - 植物 9 種，日照門檻固定。
- 只算直射光，不算雲、漫射、反射（README 有寫）。
- 有內建自檢（`index.html:1057` 起），頁面載入時跑幾個已知答案案例，結果顯示在頁面底部。它不能在終端機跑。

## 提案

規模是粗估：小＝一兩天內、中＝一週內、大＝要先研究。

### P0 底盤：抽出計算核心，讓自檢能在終端機跑
- 做什麼：把太陽計算與遮蔽幾何從 `index.html` 抽成獨立的 ES module；把內建自檢改寫成 Node 內建測試工具（`node --test`）能跑的測試。
- 為什麼：後面的提案都會動到狀態與網址結構。沒有測試，遮蔽幾何改壞了不會有人發現。
- 使用者看到什麼：沒有變化。這是安全網。
- 規模：中。

### P1 分享連結含全部陽台設定
- 做什麼：把朝向、尺寸、遮蔽物、樓層、盆栽位置、日期全部編進網址。
- 為什麼：現在只有植物進網址。朋友掃連結看到的是預設陽台，不是你的。
- 規模：小。前置：P0。

### P2 地點可選
- 做什麼：先提供台灣縣市預設經緯度，再考慮手機定位。
- 為什麼：緯度寫死台北，高雄的人算出來的是台北的太陽。
- 規模：小到中。前置：P0。

### P3 記住上次設定
- 做什麼：用瀏覽器本機儲存記住最後一次設定。
- 為什麼：每次打開都要重填，就不會有人常用。
- 規模：小。

### P4 用氣象資料校正（待研究）
- 做什麼：用各月雲量或日照時數資料，在直射估算旁加一條「考慮雲量後」的參考線。
- 為什麼：台北多雲，只算直射光的誤差不小。這條決定使用者信不信這個數字。
- 待查：氣象署開放資料有沒有合用的項目、授權怎麼標。**資料源沒查證前不要動手。**
- 規模：大。

### P5 實測對照
- 做什麼：讓使用者輸入手機照度計量到的值，跟估算值並排。
- 為什麼：讓人用自己的陽台驗證這個工具，比任何說明都有說服力。
- 規模：中。

### P6 植物庫擴充與自訂門檻
- 做什麼：加更多蔬菜香草；允許使用者改日照門檻。每種植物維持附來源連結的慣例。
- 規模：小，但每種植物都要找到來源。

### P7 反向推薦
- 做什麼：選好植物，系統告訴你哪一格、哪幾個月最適合。
- 為什麼：從「算數字」變成「給建議」。
- 規模：中。前置：P0、P6。

## 建議順序

P0 → P1、P2、P3（三個可以平行）→ P5 → P6、P7 → P4。
P4 排最後，因為資料源還沒查。

## 還沒決定、想聽大家意見的事

1. **給誰用？** 全台灣任何人，還是先只給自己和朋友？答案決定 P2 要不要做。
2. **要不要引進 npm 工具鏈？** 目前零依賴，打開 `index.html` 就能跑，推到 main 就上線。
   引進打包工具會多一層 build，但可以有型別檢查與 lint。P0 用 `node --test` 兩種選法都能做。

## 怎麼開始

- 直接用瀏覽器開 `index.html`，不用裝任何東西。
- 改完看頁面底部的自檢有沒有全過。
- 開分支、開 PR，PR 描述寫對應的提案編號。
